# P3.2 — x86-64 UEFI executable smoke target

Status: **BOOTX64.EFI PE32+ compile verified on a local Linux Clang/LLD host**.
QEMU/OVMF firmware execution is **NOT verified** here (QEMU and OVMF unavailable).
This is a loader *entry smoke test only*, not the full NOVA kernel boot.

## What exists

- `boot/uefi/entry.c`: x86-64 UEFI `efi_main` using the Microsoft x64 ABI.
  Validates the UEFI system table signature, initializes QEMU-compatible
  COM1 and prints `NOVA-UEFI-X64-ENTRY-OK` and
  `NOVA-UEFI-P3.2-SMOKE-ONLY` before returning EFI_SUCCESS.
- `tools/uefi.py`: separate Clang/LLD PE32+ build; validates machine
  0x8664, PE32+ header, EFI application subsystem (10), marker presence;
  places EFI image at `build/uefi/esp/EFI/BOOT/BOOTX64.EFI`.
- Optional isolated QEMU test uses an in-memory read-only FAT ESP,
  no networking or host block-device pass-through, and requires an
  explicit OVMF firmware path. Split OVMF_CODE/OVMF_VARS mode makes
  a disposable writable copy under `build/uefi/`.
- `tools/nova.py` and the existing x86-32 BIOS build were not edited.

## Build (Clang and LLD Linker needed)

```sh
python tools/uefi.py build
```

Success marker: `UEFI-PE-OK`. The build does not need VirtualBox or QEMU.

## Boot smoke test in QEMU/OVMF (not yet executed)

For a *unified* OVMF.fd:

```sh
python tools/uefi.py test-qemu --ovmf /path/to/OVMF.fd
```

For split CODE + VARS images:

```sh
python tools/uefi.py test-qemu --ovmf /path/to/OVMF_CODE.fd --ovmf-vars /path/to/OVMF_VARS.fd
```

The harness requires both serial markers in `build/uefi/qemu-serial.log`
and otherwise exits nonzero. Some firmware packages use a different
OVMF image layout or firmware boot manager settings and may need
environment-specific integration before this gate works.

## Evidence and limits

A local equivalent copy of the EFI entry compiled using Clang
(`-target x86_64-pc-windows-msvc`) and `lld-link`; the resulting
PE32+ was 2048 bytes with machine `0x8664`, magic `0x20b`,
subsystem `10` and both markers embedded. This validates object and
image format **only**, not firmware execution or serial delivery.

P3.2 is not done until a real OVMF/QEMU run sees
`NOVA-UEFI-X64-ENTRY-OK` in serial and the x86-32 regression
suite remains green. The next engineering task, P3.3, is memory-map
lifecycle and a controlled ExitBootServices + 64-bit kernel handoff.

This diagnostic uses legacy x86 COM1 ports and MUST NOT be treated
as a hardware-independent UEFI serial driver. Physical hardware
installation, firmware flashing, disk partitioning and bootloader
replacement are out of scope.
