# P3.5.1 — Post-UEFI memory-map validation (first increment)

**Status: committed for local build and VirtualBox tests; execution NOT yet verified.**

This checkpoint preserves P3.4's independent ELF boot mechanism and extends
the handoff ABI. After successfully calling `ExitBootServices`, the EFI loader
passes the *raw UEFI memory-map buffer* and its byte count and descriptor stride
to the ELF kernel in x86-64 System V registers RDI, RSI, RDX.

The kernel checks descriptor sizes, record count (max 512), aligned physical
addresses, nonzero page counts, arithmetic overflows, known descriptor types,
and overlapping physical ranges. The buffer is stored in loader-owned memory
that remains mapped under the firmware's current page tables.

Expected serial markers:

```text
NOVA-UEFI-X64-ENTRY-OK
NOVA-UEFI-ELF-FILE-OK
NOVA-UEFI-ELF-LOAD-OK
NOVA-KERNEL-ELF64-ENTRY-OK
NOVA-KERNEL-P3.5-MEMMAP-VALID-OK
```

If the last marker is instead `NOVA-KERNEL-P3.5-MEMMAP-INVALID`, the
memory-map validation **failed**. The P3.5.1 runtime gate is not passed.

To build in Windows Git Bash with LLVM:

```bash
export PATH="/c/Program Files/LLVM/bin:$PATH"
python tools/uefi.py build
python tools/make_uefi_disk.py
```

Do not overwrite the verified P3.4 VDI. Convert the raw disk image into a
new named VDI for P3.5 and attach it only while `NOVA-OS-UEFI` is powered off.

**Not included:** allocation/reclamation from identified conventional
memory, ownership of page tables, GDT/IDT, CPU exception handlers,
interrupt-controller configuration, production graphics or physical boot
support. This is input validation only, and neither correctness nor execution
on VirtualBox has been established until the user runs the new image.
