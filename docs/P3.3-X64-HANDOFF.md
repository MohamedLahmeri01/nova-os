# NOVA P3.3 — x86-64 post-UEFI kernel-entry proof

Status: **compiled + PE32+ link-checked locally; VirtualBox handoff NOT YET RUN**.

## Precisely what this increment does

- EFI `efi_main` reads the firmware memory map with bounded (32 KiB) loader-owned storage.
- It validates descriptor size/count and retries a stale memory-map key up to four times.
- After `ExitBootServices` returns success, it switches to a private 32 KiB stack,
  then calls `nova_kernel_x64_entry` compiled from
  `kernel/arch/x86_64/early.c` using the Microsoft x64 ABI.
- That distinct entry prints `NOVA-KERNEL-X64-ENTRY-OK` and halts the vCPU.
- The existing x86-32 BIOS/VirtualBox build is unchanged.

**Important:** the kernel entry is presently *linked within the EFI PE32+ image*.
This is not yet an independent kernel ELF/PE binary. It relies on UEFI-provided
page tables and preserved loader-image mappings, has no IDT, no PMM ownership,
no driver stack, no filesystem and no userspace. No runtime services are used
after ExitBootServices. Do not deploy to physical hardware.

## Validation

On the Windows development host in PowerShell:

```powershell
cd D:\nova-os
git fetch origin
git switch feature/device-profiles-p1
git pull --ff-only
$env:Path = "C:\Program Files\LLVM\bin;$env:Path"
python tools/uefi.py build
```

Expected **build-only** result: `UEFI-PE-OK`. Build image is placed under
`build/uefi/esp/EFI/BOOT/BOOTX64.EFI`. The linked image contains the new kernel marker.

For VirtualBox, shut down only the disposable `NOVA-OS-UEFI` VM before
updating disks. Use the existing local `tools/make_uefi_disk.py` image
builder (from the earlier P3.2 test), then convert to a **new** VDI filename
(`nova-uefi-p33.vdi`) and attach it only to the `NOVA-OS-UEFI` VM.
Do not overwrite the VDI attached to a running VM.
Never run diskpart, format a physical disk, or touch other VMs.

The success markers in the new VM serial log should appear in order:

```text
NOVA-UEFI-X64-ENTRY-OK
NOVA-KERNEL-X64-ENTRY-OK
```

Unlike P3.2, after a successful handoff, the VM is expected to **remain
running** at a blank/unchanged screen because the early kernel executes
`cli; hlt` in an infinite loop rather than returning to the EFI menu.

A missing kernel marker is a **failed/unknown P3.3 test**, not success.
Preserve serial output and VirtualBox logs before debugging. The previous
P3.2 marker `NOVA-UEFI-P3.2-SMOKE-ONLY` will not appear in this new image.

## Further gates before the 64-bit kernel can be called operational

- Verify P3.3 live on VirtualBox (and preferably QEMU/OVMF independently).
- Run old x86-32 `python tools/nova.py test` and `python ci/gate.py`.
- Introduce an independently loaded kernel image and reviewed handoff ABI.
- Allocate/control own 4-level page tables, W^X/NX memory permissions,
  GDT/IDT, exceptions, interrupt-controller state and kernel-owned memory.
- Add memory map normalization/ownership for handoff (P3.3 passes only sizes,
  not normalized usable-region metadata) and bound-check firmware descriptors.

No physical-machine, handheld or smartphone boot support is claimed.
